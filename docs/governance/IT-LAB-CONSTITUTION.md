# IT Lab Constitution
Version: 1.0 | Effective: 2026-10-23 | Status: Foundational
Canonical: docs/governance/IT-LAB-CONSTITUTION.md
Compact layer: docs/governance/PROJECT-INSTRUCTIONS.md

## 1. Mission and success
IT Lab is a hands-on technical laboratory, professional technology community and maintained knowledge ecosystem. Its outputs are tested solutions, software, infrastructure automation, educational technology, professional learning and reproducible guidance. Visibility, documentation and marketing support these outputs; document quantity or follower count alone is not success. Success requires functional results, evidence, safe sharing, long-term retrieval and community reuse.

## 2. Authority and governance
Higher-priority platform and safety instructions take precedence. Explicit authorized user requests govern the requested scope. The compact Project Instructions are usable independently and must stay within 8,000 characters; this constitution explains their detailed meaning without overriding them. Domain standards are subordinate to both. A new draft is not adopted policy until committed and referenced from the changelog. Version decisions and their rationale in GOVERNANCE-CHANGELOG.md. Resolve conflicting source facts by reviewing evidence, not erasing the disagreement.

## 3. First-class technical domains
Support Windows 10/11, PowerShell, deployment and drivers; Linux/NixOS, declarative builds, networking and services; Active Directory, Group Policy, Entra ID, Microsoft 365 and Intune; Wi-Fi, TCP/IP, DNS, DHCP, routing, VLANs, firewalls; hardware, peripherals, printers and electronics; Python, Bash, web programming, APIs and GitHub; Google Workspace Education, Apps Script and school workflows; cloud services, automation and professional IT collaboration. Technical decisions must be requirement- and evidence-led, not vendor-first.

## 4. Architecture and role boundaries
Keep system logic, workflow, source code, configuration, data, documentation, educational content, user interface and social communication in distinct artifacts. Infrastructure owners validate operations and backup/rollback. Developers maintain code and tests. Knowledge maintainers curate canonical procedures and metadata. Google Docs collaborators contribute proposals and edits. Community moderators maintain safe, organized discussion without implicitly controlling production systems. Outreach managers handle approved publication without altering technical evidence. Automations document triggers, inputs, outputs, privileges, idempotency, failure handling and proof of action. One person can perform several roles without collapsing their responsibilities.

## 5. Languages and accessibility
English is standard for governance, architecture, indexes, metadata, internal reference documents and technical identifiers. Georgian is standard for user-facing instructions, educational resources, troubleshooting and handouts. Georgian documents remain Georgian in either repository; the knowledge register metadata is English. Honor explicit alternate-language requests. Tutorials use concrete procedures, exact filenames, expected results and verification. Explanations to children must use age-appropriate language; administrative and student-facing guidance must be separate.

## 6. Evidence-driven engineering lifecycle
Discover → design → implement → test → document → index → communicate. Gather system version, intended outcome, observed behavior, exact error, relevant command output/logs and recent changes. Classify failures by evaluation, build, activation, boot, runtime, data, UI, workflow or connectivity when it sharpens diagnosis. Form narrow testable hypotheses; prefer one reversible change per step. Before risk, identify scope, privilege, backup, rollback and success criteria. Label steps observed, verified, failed, recommended or unknown. Never invent shell commands, API contracts, observed success, execution state or source citations. Verify changing platform facts against primary up-to-date documentation. An operational issue can be closed as verified only with a reproducible check or directly observed correct outcome.

## 7. Canonical storage and path continuity
GitHub repository: https://github.com/avtotrainer/ITLab. Google Drive: https://drive.google.com/drive/folders/10O4HBIpzouxzKLl_CmL60__4domJKcB9. GitHub Markdown is canonical for governance, code, configurations, runbooks and knowledge articles. Google Docs is the collaboration/reading representation. Slack and other messaging are discussion surfaces, not long-term reference libraries. Keep README.md as navigation, docs/governance/ as operating policies, docs/knowledge/ as registers/architecture. Additional topic directories are created only when real content warrants them. The existing HP printer article stays at docs/nixos/HP-LASERJET-M102W-WIFI-CUPS-HANDOUT.md unless its migration and backlink updates are explicitly approved. No empty directory trees, silent file renames or duplicative parallel canons.

## 8. Documentation quality
DOCUMENTATION-STANDARD.md defines metadata and review. A Georgian technical handout captures the original incident and environment, the commands actually tried, what failed and why, the successful steps, meaningful alternatives, exact file paths, reset/recovery/rollback, hazards, expected result, one repeatable verification and remaining unknowns. Distinguish tested facts from recommendations. Record versions, verification date, publication classification and triggers for future review. A runbook adds prerequisites, impact, preflight, execution, post-check, contingency and restore points. Audit the full resolution history before releasing a shortened tutorial.

## 9. Knowledge lifecycle and synchronization
Create an entry in docs/knowledge/KNOWLEDGE-REGISTER.md for each canonical reusable artifact. Track title, category, repository path, corresponding Google Docs URL or none, language, version, date last verified, visibility classification, sync state and related resources. Supported sync labels: canonical-only, in-sync, docs-ahead, repo-ahead, conflict, unknown. Compare current revisions before synchronizing; where Google Docs has independent changes, preserve and review them instead of silently overwriting. Read back content and parent location after all writes. Mark uncertain status unknown. Do not assume a connected Google Doc automatically enters ChatGPT Project Knowledge.

## 10. Security and publication
Public repositories must contain no credentials, tokens, private keys, student records, private contact lists, secret network topology or sensitive host/device identifiers. Use redacted examples and least-privilege accounts. Classify material public, community, internal or restricted. Seek explicit consent for recognizable learner content and protect minors. Do not change external permissions, share, invite, issue mass messages, open accounts, delete, execute destructive changes, launch paid campaigns, spend, alter billing, or publish new public content without explicit authorization. A task to create approved public repository documentation authorizes only the scoped public-safe files, not announcements or sharing to new audiences. Preserve user edits and connected-system boundaries. Security incidents require controlled disclosure and restricted evidence.

## 11. Slack governance
Inspect the connected workspace identity, settings, existing channels and roles before recommending changes. Do not treat Teacher Collaboration Lab as IT Lab merely because an account can access it. Slack should support onboarding, announcements, technical support, topic discussion, project coordination, decisions and moderated professional conduct. Candidate channels: #announcements, #general, #introductions, #helpdesk, #windows, #linux-nixos, #networking, #development, #edtech, #resources, #projects. Actual channel creation depends on activity; prevent duplicate and empty channels. Public channels are discoverable within the community; private channels hold legitimate restricted discussion. Purpose texts, pinned help-request guidelines, moderators and links to canonical resources must be clear. Resolved discussions produce a concise conclusion, link to GitHub/Drive, date and owner. Permissions and invitations require approval.

## 12. Community values and moderation
Invite respectful technical skepticism, source-based corrections, peer help and credit to contributors. Reject harassment, unsolicited advertising, privacy violations and fabricated expertise. Help requests should give a sanitized environment, expected and actual result, error, attempted steps and success check. Moderators explain scope and de-escalate, then intervene proportionately against repeated harm; sensitive matters move to appropriately restricted channels, never public GitHub issues. Publish clear contribution and attribution guidance. Do not auto-import contacts or treat community membership as marketing consent.

## 13. Social media strategy
LinkedIn is prioritized for professional contacts, visibility and partnerships. X is for concise IT learnings, discussion and international participation. Facebook, YouTube, Instagram and other platforms are optional only for defined audience and maintainable formats. Identity setup should provide accurate biography, coherent visual language, official links and accessible posts. Public copy gives one practical message and evidence or an example. Default to succinct Georgian; adapt for English-speaking audiences as needed. No invented project results, reach, partnerships, endorsements or quotes. Require review of license, technical accuracy, consent, tone and publishing permissions.

## 14. Organic and paid campaigns
Campaign plans contain objective, target audience, platform/rationale, core offer, format/creative, organic or paid distribution, budget/duration when paid, CTA, destination, metrics/KPIs, risk/privacy and evaluation/optimization. Organic campaigns can demonstrate verified tips, projects, educational tools, useful handouts, events and community conversations. Paid media may include LinkedIn Ads, X Ads and Meta Ads after current official policy verification. Run small measured experiments if approved; evaluate meaningful contribution, not only impressions. Separate proposal, approval, launch and post-campaign report. Never change billing or spend without direct explicit authority.

## 15. Messaging ecosystem
Compare Telegram, WhatsApp and WhatsApp Business, Signal, Messenger, Discord and Teams by audience, privacy, admin controls, moderation, access, cost, integrations and ongoing maintenance. Do not create accounts or groups for completeness. Slack remains professional structured collaboration, while an appropriate messenger can handle a bounded audience or notifications. Messenger discussions do not replace canonical GitHub/Drive knowledge. Provide Georgian setup guidance, invite safety, backup administrators, privacy and retention cautions.

## 16. Change management and operational assurance
Before external mutation: identify destination, existing state, authorization, possible loss, minimal change and validation. Preserve stable paths and user-authored text. Prefer reviewable commits, revision-safe updates and tested scripts over ad hoc edits. Read back files, links and modified resources, including destination folders and permissions where available. Log governance revisions in GOVERNANCE-CHANGELOG.md. Report verified completion distinctly from uncertain or rejected actions. When connector access is wrong or absent, halt changes to that service and give a manual onboarding path instead.

## 17. Review and success indicators
Review governance after significant workflow/security/integration changes, and runbooks after important upstream versions change. Monitor percentage of solved issues documented with verification, knowledge items with stale/unknown status, broken links, repeatable operational successes, useful community answers and safe approved outreach. Keep a human owner for maintenance. Archive deprecated procedures without rewriting the historical record.
